# 整体迭代计划（项目开发规划）

> 所属项目：可配置化超大文件数据解析服务
> 文档类型：迭代类（项目开发规划）
> 上游依据：`../design/01-总体设计.md` 及 `../design/02`~`10` 各模块详细设计
> 关联目录：`../design/`（设计类）、`../test/`（测试用例设计）、`../references/`（附录与校验）

本计划说明系统从零到可发布的整体开发规划。采用**依赖驱动、分层推进**的迭代策略：当前迭代 1 先打地基（工程骨架 + 最小数据契约 + 配置 DSL），再逐层实现索引、解析、算子、调度、内存，最后集成、加固与优化。每个迭代均有明确目标、交付、验收标准与里程碑。

---

## 1. 项目目标回顾

| 目标 | 说明 |
| --- | --- |
| 解析目标 | 将半结构化超大文件（最高 80GB）解析为标准化 KV 对，文件名亦作为数据源参与解析 |
| 时间复杂度 | 处理时间随文件大小线性增长（O(N+P)），禁止指数级增长环节 |
| 内存可控 | 任何阶段内存占用有硬上限，超阈值自动 spill to disk，绝不爆内存 |
| 配置驱动 | 分块规则、解析规则、处理算子、依赖关系全部由配置文件声明，无需改代码 |
| 智能并行 | 静态分析算子依赖，自动识别串行与并行环节，生成最优执行链路 |
| 数据最小化 | 每条处理链路只持有自身最低限度的数据 |

---

## 2. 迭代策略

系统采用五层分层架构（配置 DSL 层 → DAG 调度层 → 分块索引层 → 解析执行层 → 内存管理层），各层存在强依赖关系。开发顺序遵循**自底向上、依赖先行**：

1. **迭代 1**：搭建工程骨架，确立最小数据契约（仅架构不变量：KV=键+类型化值、Block=偏移/大小零拷贝引用），并实现配置 DSL（声明的输入），使后续层可配置化。
2. **迭代 2**：实现索引扫描（第一遍读）。
3. **迭代 3~6**：依次实现解析引擎（第二遍读核心）、算子、调度、内存管理；**数据模型随各层功能按需扩展**。
4. **迭代 7~9**：集成四阶段执行流程，补齐错误处理/可观测性，再做性能优化与发布。

> 说明：内存管理（spill、有界队列）是"不爆内存"的关键，但依赖解析/算子先行产出数据流；因此将其作为独立迭代在解析与调度之后补齐，而非在最开始实现。

> **数据模型演进原则**：本系统唯一稳定的架构不变量是"数据流统一为 KV/KVSet"。该不变量在迭代 1 仅以**最小契约**确立（KV 基元 + Block 引用），足以让各层并行开工即可。具体 Value 类型、KVSet 紧凑布局、BlockMeta 字段、序列化格式等，**全部随功能开发同步创建、按需扩展**（由 parser/operator/spill 的需求反推），不在前期一次性完整定义——避免复杂项目方案反复导致的数据模型返工。每次扩展需同步更新 `../design/02-数据模型与核心抽象.md`，并纳入 `../references/99-自洽性校验报告.md` 的校验范围。

## 4. 各迭代详解

### 迭代 1 · 工程骨架、最小数据契约与配置 DSL 解析层

> **当前迭代**。本迭代合并了原「工程骨架与最小数据契约」与「配置 DSL 解析层」。其功能详细设计见同目录下的 [《迭代 1 详细设计》](迭代1详细设计-工程骨架数据契约与配置DSL.md)，该文档为本迭代**编码的唯一权威依据**（含接口定义、逻辑说明、时序图、流程图、数据推演，不含示例代码）。

- **目标**：搭建可构建、可测试的工程骨架；确立「数据流统一为 KV/KVSet」架构不变量的最小契约；让数据流链路可由一份**类型无关**的 YAML 统一节点图推断，并据此完成实现绑定与计算规划。
- **任务清单**：
  - 工程脚手架：语言/构建/依赖管理、代码目录规范、单元测试与 CI 骨架。
  - 最小数据契约：KV（键 + 类型化值）与 Block 引用（offset + size，零拷贝）的**最小定义**，仅足以支撑各层接口签名；明确 Value 类型、KVSet 紧凑布局、BlockMeta 字段、序列化格式由后续迭代按需扩展。
  - YAML 加载为统一节点图（meta/input/nodes/configs/runtime）。
  - 类型无关图校验：结构完整、children/inputs 引用、环检测、impl 绑定存在性、键契约（GraphValidator）。
  - 统一节点模型：kind（container/source/process）、结构边 children、数据流边 inputs。
  - 实现绑定：impl id 与 ImplementationRegistry；特有配置经 config/config_ref 不透明透传（取代旧 templates/ref）。
  - 键空间推演：输出/上下文键一律由 output.schema、context 声明（KeyDeducer）。
  - 生成 ExecutionPlan（图 + 绑定 + 不透明 config + 键契约 + 波次）。
- **涉及设计**：`../design/02-数据模型与核心抽象.md`、`../design/03-配置驱动DSL设计.md`；实现级详见《迭代 1 详细设计》。
- **验收**：工程可构建、单元测试与 CI 可运行；附录完整示例（`../references/11-附录.md`）可无错编译为 ExecutionPlan；非法配置（结构/环/未绑定实现/键引用落空）能给出明确报错。
- **里程碑**：M0 工程骨架、数据契约与配置能力就绪。

### 迭代 2 · 容器解析器与索引扫描（第一遍读）

- **目标**：实现**核心容器解析器模板** `BaseContainerParser.scan`（结构解析，把文件解析成块树，见 `../design/04` §3），并注册**内置容器实现**使其可运行，建立 Block offset 索引。
- **任务清单**：
  - 核心：mmap 读取与读缓冲（read_buffer_mb 默认 256）。
  - 核心：scan 模板方法与 ParseContext 上下文栈。
  - 端口实现：BoundaryMatcher 7 种边界（无状态纯函数）。
  - 端口实现：BlockIdResolver 4 种来源（marker_line/content_regex/sequence/fixed），失败 fallback sequence。
  - 端口实现：DispatchStrategy 两种（sequential 默认 / marker_driven）。
  - 内置实现注册：容器 impl `marker_block_split`（组合上述端口，见 `../design/11` §2）。
  - 文件名 source 节点 `__filename__` 注入索引首位；依赖块标记。
  - BlockMeta 紧凑索引（约 32 字节/条）。
- **涉及设计**：`../design/04-递归分块解析引擎.md`、`../design/07-大文件内存管理.md`、`../design/11-内置解析器与算子实现.md`
- **验收**：索引扫描性能符合口径（NVMe 15~30 秒 / SATA SSD 约 2.5 分钟 / HDD 约 9 分钟，按 80GB）；索引为 MB 级；不加载业务数据。
- **里程碑**：M1 第一遍读完成。

### 迭代 3 · 叶子解析器（字段解析，第二遍读）

- **目标**：实现**核心叶子解析器模板** `BaseParser.parse`（见 `../design/04` §5），并注册**内置叶子解析器实现**，与迭代 2 容器共同构成完整解析器树。
- **任务清单**：
  - 核心：parse 模板方法（套 output.schema、成键、收集上下文、组装 KVSet）。
  - 内置实现注册：`regex_extract`、`fixed_width_extract`、`json_path_extract`、`csv_extract`（含 tsv）、`kv_pair_extract`、`kv_multi_extract`、`line_fields_extract`（见 `../design/11` §3）。
  - 动态解析器 key_schema 约束（fields/on_unknown）与记录集/展开。
  - custom 解析器插件钩子（必须声明输出 schema）。
  - 父块上下文经 KeyComposer.collect_context 注入。
  - 按解析需要**按需扩展数据模型**（随各解析器实现反推补充，不提前一次性建模）。
- **涉及设计**：`../design/04-递归分块解析引擎.md`、`../design/键生成规则与数据约束.md`、`../design/11-内置解析器与算子实现.md`
- **验收**：PS/CSV/FA/KV 混合格式（附录场景三）端到端字段正确；父块 phase_id 上下文正确注入；动态解析器键约束生效。
- **里程碑**：M2 核心解析能力完成。

### 迭代 4 · 算子执行模型

- **目标**：实现**核心算子模板** `BaseOperator`（见 `../design/05`），并注册**内置算子实现**与插件机制，获得 KV 计算与衍生能力。
- **任务清单**：
  - 核心：IOperator 生命周期与 execute 模板（投影、to_short_name、compute、碰撞检测、成键、上下文传播、组装）。
  - 核心：输入选择器（keys/key_prefix/key_pattern/all）与输出契约。
  - 内置实现注册：`enrich_join`、`group_aggregate`、`map_transform`、`predicate_filter`、`hash_or_merge_join`、`key_deduplicate`（见 `../design/11` §4）。
  - custom 算子插件机制（必须声明输出 schema）。
  - 按算子 I/O 需要**按需扩展数据模型**（聚合中间类型、join key 表示等，随实现反推）。
- **涉及设计**：`../design/05-算子执行模型.md`、`../design/键生成规则与数据约束.md`、`../design/11-内置解析器与算子实现.md`
- **验收**：各内置算子及其组合链单元测试通过（正常/空输入/超大/错误/并发）；输出碰撞与别名规则生效。
- **里程碑**：M2 计算能力完成。

### 迭代 5 · DAG 与并行调度

- **目标**：静态分析依赖，生成最优并行执行链路。
- **任务清单**：
  - DAG 构建：节点集合、边推导、DFS 环检测、节点标注。
  - Kahn 拓扑排序与波次划分。
  - 串行依赖识别（严格串行/共享依赖/传递依赖/独立分支）。
  - 并行链路生成：链路合并/拆分/依赖聚合/LPT 排序。
  - 事件驱动调度器：READY/RUNNING/COMPLETED/WAITING 四集合。
  - 投影下推与链路数据最小化。
- **涉及设计**：`../design/06-依赖分析与并行调度.md`
- **验收**：依赖图构建正确；串行/并行节点识别正确；波次划分正确；并行度随 storage_medium 动态调整。
- **里程碑**：M3 调度能力完成。

### 迭代 6 · 内存管理与 Spill

- **目标**：确保任何阶段内存有硬上限，绝不 OOM。
- **任务清单**：
  - 有界队列 + 背压：Block 队列（256MB）、KV 队列（10000 条或 128MB）、算子输入队列（64MB）。
  - Spill to Disk：append-only 格式、流式回放、自动清理。
  - 跨块依赖三策略：投影预物化 / 外部排序 / 分桶哈希。
  - 两遍扫描与末尾依赖场景。
  - 峰值内存公式验证（默认配置 ≈ 2.8GB）。
- **涉及设计**：`../design/07-大文件内存管理.md`
- **验收**：超大输入下峰值内存符合公式、不 OOM；spill 正确回放；末尾依赖两遍扫描正确。
- **里程碑**：M3 内存保障完成。

### 迭代 7 · 端到端执行流程集成

- **目标**：四阶段串联，跑通完整任务。
- **任务清单**：
  - 阶段一：配置加载与 DAG 构建（含依赖块识别）。
  - 阶段二：索引扫描（第一遍读）。
  - 阶段三：数据加载与处理（第二遍读，依赖块优先 + 其他块流式，每块只读一次）。
  - 阶段四：结果输出与清理（输出目标、unmap、执行统计）。
  - 源文件逻辑两遍读取保证。
- **涉及设计**：`../design/08-执行流程详解.md`、`../design/01-总体设计.md`
- **验收**：按附录配置跑通端到端任务，产出正确 KV；逻辑读取两遍；依赖块不重读。
- **里程碑**：M4 主线贯通（可端到端出结果）。

### 迭代 8 · 错误处理与可观测性

- **目标**：健壮性与可观测性。
- **任务清单**：
  - 错误分类与处理策略（配置/分块/解析/算子/IO/内存）。
  - 断点续跑：检查点（每 1000 Block 或 30 秒）、幂等保证。
  - 进度监控与性能指标采集（Prometheus metrics + 日志）。
- **涉及设计**：`../design/09-错误处理与可观测性.md`
- **验收**：断点续跑正确、幂等不重复输出；指标与错误日志输出完整。
- **里程碑**：M4 健壮性完成。

### 迭代 9 · 性能优化与发布

- **目标**：达到线性时间、有界内存目标，准备发布。
- **任务清单**：
  - 并行度调优与存储介质适配（HDD/SATA SSD/NVMe）。
  - HugePages 大页支持。
  - 80GB 级压测：索引扫描、端到端耗时、内存峰值、spill 量。
  - 容器环境配置（max_heap_mb 建议 60%~70%）。
  - 性能报告与发布文档。
- **涉及设计**：`../design/10-性能与扩展性.md`、`../references/11-附录.md`
- **验收**：端到端复杂度 O(N+P)、峰值内存 O(1)；压测数据达标；发布就绪。
- **里程碑**：M5 发布。

## 7. 质量与测试策略

- 每个迭代交付均须通过该迭代验收标准，并补充对应测试用例设计到 `../test/` 目录。
- 测试覆盖：单元测试（数据模型、边界匹配、算子、调度）、集成测试（混合格式端到端）、性能测试（80GB 级压测）、异常测试（空输入/超大输入/错误配置/并发）。
- 跨迭代保持文档自洽：变更设计或口径时，同步更新 `../design/` 对应文档与 `../references/99-自洽性校验报告.md` 的校验范围。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 超大文件解析性能不达标 | 无法满足线性时间目标 | 提前在迭代 2/9 压测，优先保证索引扫描口径 |
| 内存峰值不可控 | OOM，违反核心目标 | 迭代 6 重点验证 spill 与有界队列，预留 max_heap_mb 软上限 |
| 依赖配置复杂导致易错 | 配置驱动目标打折 | 强化 Schema 校验与模板复用（迭代 1） |
| 并行调度与内存管理耦合 | 波次/链路调度影响内存 | 迭代 6 与迭代 5 联合联调，明确接口契约 |
| 需求/范围变更 | 打乱排期 | 里程碑评审点确认范围，变更走迭代记录 |

## 9. 迭代完成定义（DoD）与回顾

每个迭代的完成需同时满足：

1. 本迭代任务清单全部完成。
2. 验收标准全部通过（含对应测试用例）。
3. 相关设计文档与代码口径一致、无冲突；**迭代 1 起以《迭代 1 详细设计》为编码唯一权威依据**。
4. 测试用例设计归档到 `../test/`。

建议每迭代结束进行回顾：核对实际产出、耗时、遗留项，并将迭代结果/变更记录归档到 `iterators/` 目录。
