# 04 · 分块解析引擎（核心抽象）

> 所属项目：可配置化超大文件数据解析服务
> 文档类型：模块详细设计（分块解析引擎 · 核心框架）
> 上游依据：[01-总体设计.md](01-总体设计.md)、[02-数据模型与核心抽象.md](02-数据模型与核心抽象.md)、[03-配置驱动DSL设计.md](03-配置驱动DSL设计.md)

## 1. 模块定位与上下游

半结构化数据的核心特征是「格式混布嵌套」：文件由多种块混布组成，块内可有不同子结构，子结构还能继续嵌套。本模块把"将文件解析成块树、将块解析成 KVSet"统一为**同一种递归下降解析动作的两个粒度**，并以抽象基类固化与业务格式无关的全部动作。

| 方向 | 模块 | 关系 |
| --- | --- | --- |
| 上游 | 03 配置 DSL | 提供统一节点图；节点经 `impl` 指定解析器实现、经 config/config_ref 提供不透明配置 |
| 上游 | 07 内存管理 | 提供 mmap 区域、读缓冲；scan/parse 在其上零拷贝工作 |
| 下游 | 05 算子执行 | 叶子解析器产出的 KVSet 是算子的输入（SourceNode） |
| 下游 | 06 调度 | BlockIndex 为按需加载与波次调度提供块位置与层级 |
| 横切 | 键生成规则 | 成键与上下文由 KeyComposer 在基类内统一完成 |

**装配关系**：Assembler 按节点 `impl` 向 ImplementationRegistry 请求解析器实例，注入不透明 config，递归组装成解析器树。框架只持有抽象基类类型，不引用具体解析器类。

## 2. 统一解析器抽象：IFormatterParser

"将文件解析成文件块"与"将文件块解析成 KV"是同一递归过程在不同节点上的表现，统一在一个接口下：

| 成员 | 签名 | 说明 |
| --- | --- | --- |
| node_id() | -> string | 对应节点 id（上下文/溯源命名依据） |
| kind() | -> container / source | 节点类别 |
| scan(region, ctx) | -> list[BlockMeta] | 结构解析：容器实现，叶子返回自身 BlockMeta |
| parse(block, ctx) | -> KVSet | 字段解析：叶子实现，容器不产出业务 KV |

**两类解析器（同一抽象的两种基类）：**

| 解析器基类 | 对应 kind | 产物 | 执行遍次 |
| --- | --- | --- | --- |
| `BaseContainerParser` | container | 子块 BlockMeta（块树）+ 维护上下文栈 | 第一遍（索引扫描） |
| `BaseParser` | source | KVSet | 第二遍（数据加载） |

字节数据通过 mmap 区域的 offset+length 引用全程零拷贝传递，解析器树每一层都不复制数据。

## 3. 容器解析器：BaseContainerParser 与 scan 模板

容器解析器把"边界切分、实例身份解析与上下文压栈、子块递归调度"这些与业务字段无关的动作以 **final 模板方法 `scan`** 固化；具体容器只提供三个可插拔端口的实现（由不透明 config 装配），不自行拼块。

### 3.1 可插拔端口（接口，核心不写死实现）

| 端口 | 接口契约 | 职责 |
| --- | --- | --- |
| BoundaryMatcher | `find_instances(region) -> list[(start,end)]`，无状态纯函数 | 在父区域内确定本容器每个实例的 [start,end) |
| BlockIdResolver | `resolve_id(instance_region) -> id \| None` | 解析块实例身份；失败返回 None 由基类 fallback 为 sequence |
| DispatchStrategy | `enumerate_children(region, ctx) -> list[(child_node, child_region)]` | 决定每个子块的范围、类型与顺序 |

> 这三个端口是**抽象扩展点**。随系统交付的具体匹配/解析/调度实现（起始标记、单行、到下一标记、到块尾、分隔符、定长、EOF 等）属于内置实现库，见 [11](11-内置解析器与算子实现.md)；核心不枚举它们。

### 3.2 scan 模板方法固定步骤

```mermaid
flowchart TD
    A[scan(region, ctx)] --> B[BoundaryMatcher.find_instances<br/>定位本容器每个实例起止]
    B --> C[逐实例 BlockIdResolver.resolve_id<br/>失败 fallback sequence]
    C --> D[将 node_id 与实例身份压入 ParseContext<br/>并写入本容器 BlockMeta]
    D --> E[DispatchStrategy.enumerate_children]
    E --> F{子节点 kind}
    F -->|container| G[递归 child.scan]
    F -->|source| H[记录叶子 BlockMeta<br/>字段解析留到第二遍]
    G --> I[汇总 BlockMeta 追加到 BlockIndex]
    H --> I
```

容器解析器**不产出数据键/业务 KV**，只产出 BlockMeta 并维护上下文栈；上下文键（`{祖先 node_id}.{身份字段}`）的源头即此处压栈，叶子解析器在第二遍通过 KeyComposer.collect_context 收集（见 [键生成规则与数据约束.md](键生成规则与数据约束.md)）。

### 3.3 索引扫描算法（第一遍，通用）

索引扫描即根容器 `scan` 的执行，目标是建立全文件 BlockMeta 索引（node_id、实例身份、offset、size、depth、parent）。

1. **准备**：各容器从自身不透明 config 取得端口实现，构建匹配状态；DSL 不感知标记细节。
2. **快速预筛选**：若实现支持前缀，先用短前缀做 SIMD 字节搜索定位候选位置，过滤绝大多数非候选内容。
3. **精确匹配**：对候选执行 BoundaryMatcher，确定实例边界与归属。
4. **身份解析与落盘元数据**：BlockIdResolver 解析身份，写 BlockMeta；递归进入子容器。

**块边界与大小**：实例 [start,end) 由 BoundaryMatcher 给出；同级相邻实例通常 end(i)=start(i+1)，最后一个实例结束于父区域末尾；size=end-start。

**BlockIndex 结构**：BlockMeta 的紧凑数组 + 按 parent 组织的层级索引 + 按 node_id 的二级索引；单条 BlockMeta 固定大小（见 [02](02-数据模型与核心抽象.md)、[07](07-大文件内存管理.md)）。

### 3.4 索引扫描性能口径

多模式匹配 + 预筛选整体为 O(N) 线性扫描，约等于磁盘顺序读上限，内存仅读缓冲与匹配器状态。80GB 索引扫描统一耗时口径（与 [08](08-执行流程详解.md) 一致）：

| 介质 | 80GB 耗时 |
| --- | --- |
| NVMe | 15~30 秒 |
| SATA SSD | 约 2.5 分钟 |
| HDD | 约 9 分钟 |

> 复杂标记的行级匹配比单分隔符扫描慢约 3~5 倍，此为原因说明，非耗时口径。

## 4. 子块调度：DispatchStrategy

DispatchStrategy 决定父块字节如何在子节点间分配。核心定义两种抽象调度语义；具体由实现按不透明 config 提供。

### 4.1 sequential（顺序固定，默认）

按 children **声明顺序**依次消费父区域：第一个子节点消费从当前位置开始的第一段，结束后推进偏移，第二个子节点从新位置开始，直到所有子节点消费完毕或父区域结束。适用于块内子块顺序固定的场景（多数半结构化格式）。

### 4.2 marker_driven（标记驱动）

各子节点由其在内容中匹配到的标记动态确定归属：扫描父区域时匹配到某子节点标记，其后直到下一标记（或父区域结束）的内容归属于该子节点。适用于块内子块顺序不固定的场景，策略需维护"当前数据归属"状态。

> 两种语义只描述"如何决定子块范围与顺序"，不绑定任何具体格式；标记本身由 BoundaryMatcher 实现识别。

## 5. 叶子解析器：BaseParser 与 parse 模板

叶子解析器（kind=source、无 children）是 KV 的产出点。`parse` 为 final 模板方法，把"套用键模式约束、成键、上下文注入、规范化、组装 KVSet、spill"全部固化；具体解析器**只实现一个 extract 钩子**。

| 成员 | 可见性 | 契约 |
| --- | --- | --- |
| parse(block, ctx) -> KVSet | **final 模板方法** | 按 5.1 固定步骤执行 |
| extract(block) -> ParseResult | **抽象钩子（子类唯一需实现）** | 只从字节得到 field_name -> value（或记录集），不拼键、不加前缀、不注入上下文 |
| 输出契约 | 由节点 output（namespace + schema）提供 | 约束产出键空间；未在 schema 声明的字段不进入下游 |

### 5.1 parse 模板方法固定步骤

```mermaid
flowchart TD
    A[parse(block, ctx)] --> B[extract(block) 得到原始字段/记录集]
    B --> C[按 output.schema 约束键空间<br/>未知字段按策略处理]
    C --> D[记录集展开为 field->value]
    D --> E[KeyComposer.compose_data_key<br/>namespace + field]
    E --> F[KeyComposer.collect_context<br/>收集祖先上下文键]
    F --> G[字段规范化/类型转换<br/>失败保留原值并告警]
    G --> H[组装 KVSet；超阈值由基类 spill]
```

- 成键、前缀、上下文、KVSet 布局、spill 均不由具体解析器处理；实现者只关注"如何从字节提取字段"。
- 字段名从何而来、哪些可静态枚举，属于具体解析实现的特性，统一在 [11](11-内置解析器与算子实现.md) 与 [键生成规则与数据约束.md](键生成规则与数据约束.md) 中说明。
- 叶子 KVSet 注册为数据流图的 SourceNode，供算子经 inputs 引用。

## 6. 上下文递归传递

容器解析出实例身份后，该身份自动沿 parent 链传递给所有后代，使子块 KV 携带祖先上下文，解决"子块数据不知属于哪个父实例"的问题，无需在算子层再做关联。

1. 容器解析身份后，将 `(node_id, 身份字段, 值)` 压入 ParseContext。
2. 递归处理子节点时，子节点继承并累积该上下文。
3. 叶子产出 KVSet 时，KeyComposer.collect_context 将全部祖先上下文作为隐式上下文键注入。
4. 上下文键命名：`{祖先 node_id}.{身份字段}`，如 `phase_block.phase_id=...`。
5. 节点可声明不继承某层上下文，适用于子块自身已有完整标识的场景。

多层嵌套时每层身份都注入，形成完整层级标识链。

---

## 7. 文件名 source 节点

文件名是一等数据源：在 DSL 中为 id 固定 `__filename__` 的 source 节点，由 `input.filename_node` 绑定，在索引扫描前置于 BlockIndex 首位。它与普通 source 完全相同——按 `impl` 绑定解析器、用 output 契约声明产出（默认 namespace 为 `file.`），特有配置在 configs 中。

文件名字段可被任意 process 经 inputs `from: "__filename__"` 引用，与普通块字段无区别。
