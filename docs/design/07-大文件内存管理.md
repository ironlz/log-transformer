# 07 · 大文件内存管理

> 所属项目：可配置化超大文件数据解析服务

> 上游依据：[01-总体设计.md](01-总体设计.md)、[02-数据模型与核心抽象.md](02-数据模型与核心抽象.md)、[03-配置驱动DSL设计.md](03-配置驱动DSL设计.md)、[06-依赖分析与并行调度.md](06-依赖分析与并行调度.md)

---

## 1. 内存挑战分析

80GB 半结构化文件的解析面临四重内存挑战：

| 挑战 | 说明 | 严重程度 |
| --- | --- | --- |
| 全量 KV 累积 | 80GB 文件解析后 KV 可能膨胀到 100GB+，全量加载必然 OOM | 致命 |
| 跨块依赖等待 | 依赖块在文件尾部时，前面所有块的 KV 需要等待依赖就绪才能处理 | 高 |
| 数据膨胀 | 算子衍生新 KV（如维表关联补充维度字段）导致数据量增长 30%~200% | 中 |
| 并行中间状态 | 多条链路同时执行，每条链路持有中间 KVSet，内存叠加 | 中 |

---

## 2. mmap 零拷贝读取

文件通过内存映射（mmap）映射到进程虚拟地址空间，这是大文件处理的基础：

- **不占用进程堆内存**：mmap 区域由 OS page cache 管理，不计入进程堆使用量。
- **零拷贝**：Block 通过 byte slice 直接引用 mmap 区域，解析器在引用上操作，无内核态到用户态的数据拷贝。
- **OS 自动调页**：缺页中断时 OS 异步加载对应 page 到 page cache，常用 page 自动缓存。
- **大页支持**：启用 HugePages 减少 TLB miss，80GB 映射场景下性能提升明显。
- **64 位地址空间**：80GB 文件映射无压力（虚拟地址空间达 TB 级）。

---

## 3. offset 索引与按需加载

第一遍索引扫描只建立 BlockMeta 索引表，**不加载任何块数据**：

- **索引表极小**：每条 BlockMeta 约 32 字节（blockId 哈希 + offset + size + level + parentId），8 万个块仅 2.5MB。
- **按需加载**：第二遍执行时，根据 DAG 调度只加载当前需要的 Block，通过 `mmap[offset:offset+size]` 直接引用。
- **随机读优化**：当前波次需要加载的 Block 按 offset 从小到大排序后顺序读取，将随机读转化为跳跃式顺序读。
- **相邻合并**：offset 相邻的 Block 合并为一次大读，减少系统调用和 seek 次数。
- **智能跳过**：DAG 中未被引用的 Block 不加载，节省 IO。

---

## 4. 有界队列与背压

| 队列 | 限流维度 | 默认上限 | 背压行为 |
| --- | --- | --- | --- |
| Block 队列 | 字节数 | 256MB | 满时 IndexScanner 或子块调度器阻塞，暂停读取 |
| KV 队列 | 条数 + 字节数双维度 | 10000 条或 128MB | 满时上游解析器阻塞，暂停 KV 发射 |
| 算子输入队列 | 字节数 | 64MB | 满时上游算子阻塞，暂停输出 |

有界队列确保任何阶段的内存占用都有硬上限。背压机制自动适配上下游处理速度差，不需要手动调节速率。当下游处理慢时，上游自动降速，队列不会无限增长。

> 默认上限与 [03-配置驱动DSL设计.md](03-配置驱动DSL设计.md) 中 `max_block_queue_mb=256`、`max_kv_queue_mb=128` 口径一致。

## 5. 中间结果 Spill to Disk

当 KVSet 大小超过 spill_threshold（默认 **512MB**）时，自动将其序列化写入磁盘：

- **Spill 格式**：append-only 文件，每条记录 `[length(4 字节)][payload（紧凑二进制序列化）]`。
- **序列化**：采用 protobuf/flatbuffers 或自定义紧凑格式，避免字符串重复存储，体积比 JSON 小 50%~70%。
- **流式回放**：下游算子需要时顺序读取 spill 文件，逐条反序列化消费，不加载全量。
- **自动清理**：KVSet 被所有消费者消费后立即删除 spill 文件，释放磁盘空间。
- **磁盘空间监控**：临时目录空间不足时触发告警，降低并行度或终止非关键链路。

> spill_threshold 默认 512MB 与 [03-配置驱动DSL设计.md](03-配置驱动DSL设计.md) 中 `spill_threshold_mb` 默认值一致。

## 6. 跨块依赖的内存策略

跨块依赖（如处理器依赖块 C 和 D 的解析结果）根据依赖数据量选择三种策略：

| 策略 | 适用条件 | 实现方式 | 内存占用 |
| --- | --- | --- | --- |
| 投影预物化 | 依赖块投影后 ≤ 内存阈值（如 2GB） | 读取依赖块，只提取投影字段，构建内存 hash 表作为 lookup 维表 | 投影数据大小（通常远小于原始块） |
| 外部排序 | 依赖数据量大（> 内存阈值），join key 可排序 | 投影字段写临时文件，外部排序后做流式 merge join | 排序缓冲区大小（可控，如 256MB） |
| 分桶哈希 | join key 分布均匀 | 按 join key hash 分 N 桶写入独立文件，逐桶加载做 hash join | 单桶大小（桶数可调） |

策略选择可在配置中声明，也可运行时根据投影数据量自动选择（先尝试预物化，超阈值则自动降级为外部排序或分桶）。

---

## 7. 末尾依赖场景的两遍扫描

当所有处理都依赖文件尾部的块 D 时，采用两遍扫描策略避免全量数据留存。源文件逻辑上只被读取两遍：

**第一遍（索引扫描）**：顺序读全文件，建立 Block 索引，定位 D 的 offset 和 size。

**第二遍（数据加载与处理）**：mmap 全文件，按 DAG 依赖顺序调度，内部包含两个子步骤：

- **子步骤一（依赖块优先加载）**：通过 mmap 访问尾部的 D 块区域，执行多级分块和 KV 解析，完整 KVSet 缓存，同时投影提取依赖字段构建维表索引。D 块在 mmap 下直接访问，无需额外 seek 开销。
- **子步骤二（其他块流式处理）**：D 的依赖数据就绪后，从头顺序访问 mmap 区域解析其他块，处理器直接与 D 的维表 join。D 块的 KVSet 从缓存复用，**不重读**。

**总 IO** = 索引扫描（全文件顺序读）+ 数据加载（mmap 全文件访问，物理 IO 取决于 page cache 命中率），逻辑上两遍读取。

**内存峰值** = D 投影数据 + 流式管道常量，**与文件总大小无关**。

---

## 8. 内存占用上限保证

系统在任何情况下的峰值内存占用由以下公式界定，**不随文件大小线性增长**：

```
峰值内存 = Block 队列上限 + KV 队列上限 + 当前处理批次
         + 依赖维表数据（投影后，有上限）+ DAG 状态 + 读缓冲
```

**默认配置下**：256MB + 128MB + 128MB + 2048MB + 10MB + 256MB ≈ **2.8GB**。

补充说明：

- **mmap 区域**：由 OS page cache 管理，不计入进程堆，可通过 `/proc/sys/vm/drop_caches` 回收。
- **Spill 文件**：在磁盘上，不占内存。
- **max_heap_mb 配置项**：设置软上限，超过时调度器触发强制 spill 和降速。
- **容器建议**：容器环境下建议设置 max_heap_mb 为容器内存限制的 60%~70%，预留 OS page cache 空间。
