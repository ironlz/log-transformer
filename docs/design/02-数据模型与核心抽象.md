# 02 · 数据模型与核心抽象

> 所属项目：可配置化超大文件数据解析服务
> 文档类型：模块详细设计（数据模型与核心抽象）
> 上游依据：[01-总体设计.md](01-总体设计.md)（术语表、架构分层）

本文档定义系统统一的数据模型与核心抽象：KV 数据模型、文件块模型、节点抽象谱系与算子、处理链路模型、文件名作为数据源。这些抽象是全系统（解析层、调度层、算子层）的共同基础。

---

## 1. KV 数据模型

KV 是系统的核心数据单元，采用**分层命名空间**与**强类型值**设计。整个系统的数据流统一为 KV/KVSet 在流动，区别在于 value 的类型。

| 属性 | 说明 |
| --- | --- |
| Key | 分层命名空间字符串，如 `user.profile.name`、`event.device_id`，用点号分隔层级 |
| Value | 强类型，支持 string、int64、float64、bool、bytes、array、map、block_ref 八种类型 |
| KVSet | 一组 KV 的集合，携带来源节点 output.namespace 作为输出前缀（即 output_prefix），是节点间传递的数据单元 |
| KVRef | KV 的轻量引用（offset + length），用于堆外或磁盘存储时不持有实际数据，避免拷贝 |

### 1.1 block_ref 特殊类型与 KV 分类

Value 类型中的 `block_ref` 是特殊类型，值为 Block 引用（offset + length + mmap 区域句柄 + block_id + 祖先上下文），**不持有实际字节数据**。block_ref 类型的 KV 称为 **Block-KV**，其余类型的 KV 称为 **Data-KV**。

| KV 类型 | Value 类型 | 含义 | 出现位置 |
| --- | --- | --- | --- |
| Block-KV | block_ref | key=block_name，value=文件块引用，代表一段尚未解析的原始字节范围 | 分块器输出 → 解析器输入 |
| Data-KV | string/int64/float64/bool/bytes/array/map | key=字段名，value=具体数据值，代表已解析的结构化数据 | 解析器输出 → 算子输入/输出 |

Block-KV 使得文件块可以纳入统一的 KV 数据流模型：分块器消费父 Block-KV 产出多个子 Block-KV，解析器消费 Block-KV 产出 Data-KVSet，算子消费 Data-KV 产出 Data-KV。节点的输入输出统一为 KVSet（KVSet 可只含一个 KV），但 value 的类型参数因节点类型而异。

### 1.2 KVSet 内存表示

KVSet 的内存表示采用紧凑布局：

- **Key** 存于共享字符串表（去重）。
- **Value** 按类型序列化到连续字节区域。
- **索引数组**记录每条 KV 的偏移。

block_ref 类型的 Value 只存储引用元数据（16~32 字节），不复制原始字节，因此千万级 Block-KV 的内存驻留成本极低。这种布局将对象头开销降至最低，适合大文件解析场景。

## 2. 文件块模型

| 概念 | 定义 |
| --- | --- |
| BlockMeta | 块元数据：block_name（块类型名称）、block_id（唯一标识）、offset、size、depth（树深度）、parent_block_id（父块 ID） |
| Block | BlockMeta + 原始字节引用（mmap 区域的 byte slice，零拷贝，不复制数据） |
| 节点图结构 | DSL 的 nodes 为统一节点图，根为文件级，结构关系由 children 表达，深度由节点递归嵌套决定，不同分支深度可不同 |
| container 节点 | kind=container、有 children 的节点，负责切分子块并递归调度，不直接产出业务 KV |
| source 节点 | kind=source、无 children 的叶子节点，负责解析块内容产出 KVSet，对应数据流图的 SourceNode |
| process 节点 | kind=process 的算子节点，消费 inputs 产出衍生 KVSet |
| 文件名节点 | id 固定为 `__filename__` 的 source 节点，参与正常解析流程 |

Block 的字节引用直接指向 mmap 区域，解析器在引用上做 offset 切片，全程零拷贝。节点图遍历采用深度优先，container 切分子块后分发给子节点递归处理，source 提取字段产出 KVSet。只有当 KV 需要跨阶段传递或 spill 时才执行序列化。

### 2.1 容器节点与叶子节点的执行接口分离

容器节点与叶子节点的执行接口不同，这是递归树的关键设计：

| 节点类型 | 执行接口 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- | --- |
| 容器节点（Splitter） | `execute(input: KVSet<Block>) -> KVSet<Block>` | 单个父 Block-KV | 多个子 Block-KV | 边界匹配 + 子块调度，将父块字节范围切分为若干子块，不解析内容 |
| 叶子节点（Parser） | `execute(input: KVSet<Block>) -> KVSet<DataValue>` | 单个叶子 Block-KV | 一组 Data-KV | 按 parser 配置解析块内容，将原始字节转换为结构化 KV |

容器节点的产出仍然是 Block-KV——它把父块按 boundary 切成子块，每个子块带着 block_name 和 block_id 继续向下传递。只有到达叶子节点时，Block 才被真正「消费」为 Data-KV。

- 容器节点构成解析树的「骨架」，负责切分和路由。
- 叶子节点是解析树的「终端」，负责真正的内容解析。
- 两者同属解析层，但接口签名不同，**不应强行合并为同一个 execute 方法**。

## 3. 节点抽象谱系与算子

系统中所有可执行单元统一为 **DAG 节点**，但执行接口按节点类型分离。这遵循「调度统一、执行分离」的设计原则：调度层只依赖统一的 DAGNode 拓扑抽象，执行层按具体节点类型分发到不同的接口签名。

| 节点类型 | 泛型签名 | 输入 Value 类型 | 输出 Value 类型 | 所在层 | 职责 |
| --- | --- | --- | --- | --- | --- | --- |
| DAGNode<I, O> | `execute(input: KVSet<I>) -> KVSet<O>` | 泛型 I | 泛型 O | 调度层（抽象基类） | 统一拓扑信息：id、inputs、outputs、波次、状态、依赖关系 |
| SplitterNode | `DAGNode<Block, Block>` | block_ref | block_ref | 解析层（容器节点） | 边界匹配 + 子块调度，父 Block → 多个子 Block |
| ParserNode | `DAGNode<Block, DataValue>` | block_ref | 数据值 | 解析层（叶子节点） | 内容解析，Block → Data-KVSet，是解析层与算子层的边界 |
| OperatorNode | `DAGNode<DataValue, DataValue>` | 数据值 | 数据值 | 算子层 | KV 计算与衍生，Data-KV → Data-KV |

### 3.1 调度层与执行层的职责分离

- **调度层（DAGNode）**：只管理拓扑信息——节点 id、上游依赖、下游消费者、波次归属、执行状态、资源配额。调度器判断依赖是否就绪、分配执行资源、触发 release 回收，**不关心节点内部在做什么**。
- **执行层（Splitter/Parser/Operator）**：各自有独立的 execute 签名、错误类型、重试策略和内存管理模式。
  - SplitterNode 处理边界越界和标记匹配失败。
  - ParserNode 处理编码异常和格式不匹配。
  - OperatorNode 处理字段缺失和类型转换失败。
- **类型安全**：泛型参数 I/O 在编译期约束输入输出类型，调度层看到的是类型擦除后的 DAGNode，执行层看到的是具体类型化接口，两者互不污染。

### 3.2 递归树与算子 DAG 的关系

节点图由 SplitterNode（container）和 ParserNode（source）组成结构部分，**所有 source 叶子产出的 Data-KVSet 注册为数据流图的 SourceNode**。process 节点通过 inputs `{from: <source 节点 id>}` 引用某个叶子的输出。

SplitterNode **不出现**在算子 DAG 中，只在解析层内部工作，对算子层不可见。

### 3.3 算子（OperatorNode）

算子是配置化的处理步骤，是 DAG 的执行节点。每个算子具有以下属性：

| 属性 | 说明 |
| --- | --- |
| id | 算子唯一标识，在配置中声明，用于依赖引用 |
| type | 算子类型，决定执行逻辑（enrich/aggregate/transform/filter/join/deduplicate/custom） |
| inputs | 上游依赖声明列表，每项包含 operator（上游算子 id）和 key 选择器 |
| output_prefix | 输出 KV 的统一前缀，避免命名冲突 |
| config | 算子特定的配置参数（如 join_key、group_by、表达式） |

算子生命周期：**初始化（init）→ 输入就绪检查（ready）→ 执行（execute）→ 输出注册 → 资源释放（release）**。算子输出被所有下游消费者消费后，调度器触发 release 释放内存或删除 spill 文件。

> 算子的接口定义、Key 引用机制、内置算子与自定义扩展详见 [05-算子执行模型.md](05-算子执行模型.md)。

## 4. 处理链路模型

| 概念 | 定义 |
| --- | --- |
| Pipeline | DAG 中从根节点（SourceNode）到叶子节点的一条拓扑路径，包含有序的算子列表 |
| 链路状态 | 待执行（PENDING）、执行中（RUNNING）、已完成（COMPLETED）、失败（FAILED） |
| 链路数据隔离 | 每条链路独立持有自己的输入 KVSet 和中间结果，链路间不共享可变状态 |
| 链路投影 | 每条链路在执行前计算所需字段的最小集合（投影下推），只加载这些字段 |

> 链路的生成、合并/拆分与调度策略详见 [06-依赖分析与并行调度.md](06-依赖分析与并行调度.md)。

## 5. 文件名作为数据源

文件名被视为一等数据源，在预处理阶段包装为虚拟 Block（blockId = `__filename__`），其内容为文件名字符串。虚拟 Block 走与普通 Block **完全相同**的解析流程：可按配置的分隔符或正则进一步切分，提取字段作为 KV，输出前缀默认为 `file.`。

文件名字段可被任意算子通过 key 引用（如 `file.name`、`file.date`），与普通 Block 解析出的字段无区别。这使得文件名中的元信息（如日期、批次号、数据源标识）可以自然参与算子计算。

> 虚拟 Block 的注入时机与配置见 [04-递归分块解析引擎.md](04-递归分块解析引擎.md) 与 [03-配置驱动DSL设计.md](03-配置驱动DSL设计.md)。
